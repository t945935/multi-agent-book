# 全書文風與術語指南

本文件用於統一《多 Agent 系統架構與實戰》的正文、規格、QA 報告與出版素材用語。後續章節擴充、審稿與排版微修皆應依此檢查。

## 一、核心術語

| 建議用語 | 避免用語 | 說明 |
|---|---|---|
| 多 Agent | 多代理、多智能體 | 書名與全書主軸固定使用「多 Agent」。 |
| Agent | 智能體 | 指具備任務角色、工具權限與交付物的代理程式或 AI 工作角色。 |
| 代理 |  | 可在一般中文敘述中使用，例如「代理正在等待輸入」。若作為專有概念，優先用 Agent。 |
| 程式碼 | 代碼 | 採台灣科技書常用語。 |
| 原始程式碼 | 源代碼 | 用於 source code 語境。 |
| 範例程式碼 | 範例代碼 | 用於 examples 目錄與章節實作。 |
| 審查 | 審計 | 本書以技術審查、資安審查、審稿為主；除非明確指涉 audit 制度，避免使用審計。 |
| 品質閘門 | 品質門檻、質量門檻 | 指進入下一階段前必須通過的測試、審稿或 build 條件。 |
| 出版流水線 | 出版管線 | 中文正文優先使用「流水線」，必要時可補英文 pipeline。 |
| 微修 | 小修、微調 | Pi 章節統一使用「微修」表示小步、精準、可審查修改。 |
| 監管中樞 | 控制塔、監控中心 | Herdr 章節可用「控制塔」作比喻，但正式術語使用「監管中樞」。 |

## 三、文風原則

1. 使用繁體中文，偏台灣科技書語氣。
2. 優先使用「程式碼」、「建置」、「檔案」、「資料夾」、「執行」、「驗證」。
3. 每章需維持教學型語氣：先說問題，再說概念，接著說實作，最後說驗證與反模式。
4. 避免過度口語，例如「超強」、「神器」、「隨便跑一下」。
5. 避免過度行銷，例如「完全自動」、「零風險」、「百分之百正確」。
6. 英文術語首次出現可加括號說明，之後保持固定用法。
7. 若同一句中有多個工具名，使用一致格式，例如 `Herdr`、`OpenCode`、`Codex`。

## 四、章節固定結構建議

每章盡量保留下列元素：

1. 本章導讀
2. 問題背景或核心概念
3. 實戰範例與對應 examples 目錄
4. 驗證策略
5. 常見錯誤、反模式或風險
6. 實戰練習或檢查清單
7. 本章小結與下一章銜接

## 五、驗證方式

進行術語或文風修正後，至少執行：

```bash
bash scripts/test_all.sh
PATH="$PWD/bin:$PATH" python3 scripts/build.py
```

若只修改文件不動程式碼，測試仍應保留，因為正文中的 code fence、特殊符號或 Typst 不相容語法可能造成 PDF build 失敗。
